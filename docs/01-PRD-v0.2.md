## 1. 背景与问题

海外（东南亚 / 中东 / 拉美）的陌生人社交产品长期存在三个结构性问题：

1. **开场即阵亡**：匹配成功但双方都不开第一句。行业经验：匹配后 24h 内无消息的匹配，后续对话率极低。
   根因不是“没有话题”，而是**跨语言/跨文化不知道说什么**，且害怕说错。
2. **推荐不透明、越推越窄**：用户不知道为什么会看到某人；算法又持续强化既有偏好，造成回音室和“刷不到新人”。
3. **安全与信任**：骚扰、诈骗、冒名、未成年渗透。平台常用“AI 自动回复/机器人陪聊”提升活跃度，但**冒充真人**一旦被识破就是信任崩塌。

### 1.1 用户问题（JTBD）

- 当我刷到一个有意思的人时，我想**快速找到共同点并自然开口**，这样不至于尴尬地放弃。
- 当我语言不够好时，我想**先写好、看懂再发**，这样不会因为表达失误被误解。
- 当我想“随便聊聊”时，我想**进一个气氛好的语音房**，而不是一对一压力。
- 当我遇到不合适的人时，我想**一键举报并拉黑**，并且知道平台真的会处理。

### 1.2 目标用户

| 画像 | 特征 | 主要诉求 | 反感点 |
|---|---|---|---|
| P1 跨文化交友者（22–28，留学/外派） | 英语二语，在陌生城市 | 找能聊下去的朋友、语言练习 | 被敷衍、被“机器人”敷衍 |
| P2 语言交换者（18–25） | 主动学第二语言 | 真实语伴、纠错 | 话术模板、文化刻板印象 |
| P3 深夜陪伴者（20–30） | 夜间活跃、喜欢声音 | 低压力语音房、点歌聊天 | 尴尬冷场、被骚扰 |
| P4 谨慎新用户 | 首次使用陌生人社交 | 安全、可解释、可撤回 | 被硬推、被要求给隐私 |

## 2. 目标与指标

### 2.1 北极星

**WMS（周均有意义对话用户数）** —— 定义：UTC 周一至周日内，与同一匹配对象**互发 ≥2 条成功送达消息**，且未拉黑、未命中安全风控的用户，按用户去重计数。

为什么不是 DAU：DAU 可以被刷卡片、看房间推高，但产品真正的价值发生在“两个人聊起来了”。

### 2.2 指标树（详见 `docs/04-指标与数据看板.md`）

```
WMS
├── 匹配量 = 日活 × 发现曝光 × 喜欢率
│   ├── 发现曝光 ← 推荐召回/排序质量、新用户冷启动
│   └── 喜欢率   ← 卡片信息质量、match_hint 解释
├── 匹配→首条消息率（≥40% 目标）
│   ├── AI 破冰采纳率（建议→采纳）
│   └── 采纳→发送率（必须 100% 由用户点击）
├── 消息往返数（双方各 ≥2 条）
└── 留存（D1/D7/D30）
```

### 2.3 OKR（v0.2 上线后第一个季度）

| Objective | KR | 现状/目标 |
|---|---|---|
| O1 让匹配真正聊起来 | KR1 匹配后 24h 内有消息的匹配占比 | 基线 TBD → ≥55% |
| | KR2 AI 破冰建议采纳率 | ≥25% |
| | KR3 采纳后用户实际发送率 | ≥70%（人工发送），且 **AI 自动发送 = 0** |
| O2 让推荐可解释 | KR4 Discover 卡片展示 match_hint 比例 | 100% |
| | KR5 推荐原因被用户评价为“合理”的比例 | ≥80% |
| O3 安全与信任 | KR6 举报 24h 内首次响应率 | 100%（人工） |
| | KR7 高危举报（未成年人/诈骗）分流准确率 | ≥95%（抽样） |
| O4 系统可靠 | KR8 P0 用例发布门禁 | 100% 通过 |

## 4. 功能需求（FR）

### FR01 认证与门禁

- 邮箱验证码登录：`POST /auth/code` → `POST /auth/verify`。
- 验证码 6 位、5 分钟有效、60s 内不可重发、错 5 次锁定 15 分钟。
- **年龄与条款**在客户端先拦截（未勾选不发请求），服务端再次校验（`age_confirmed`、`terms_accepted` 必为 true）。
- 会话 7 天有效；`POST /auth/logout` 立即吊销该 token。
- Mock 模式：`POST /auth/code` 返回 `data.demo_code`（演示用，生产必须走邮件且不得返回）。

验收：TC01 / TC02 / TC03；E2E `test_age_gate_blocks_sign_in`。

### FR02 资料

- 必填：昵称（≤24）、国家、时区（IANA 或 `UTC±n`）、社交目标（1+）、兴趣（3–12）。
- 可选：语言、简介（≤300）。
- `profile_strength` = 加权完成度，用于主页进度与推荐轻微加权。
- 邮箱永不出现在他人可见数据中。
- `PATCH /users/me/profile` 支持部分字段合并；未完成必填前 `profile_completed=0`。

验收：TC04；`test_profile_strength_and_email_not_leaked`。

### FR03 字段级隐私

- 国家 / 兴趣 / 时区三个字段各自可选 `public | matches_only | private`（默认：国家、兴趣 public；时区 matches_only）。
- 非公开字段在 Discover、匹配、聊天、房间中**一律不下发**（不是前端隐藏）。
- 修改可见性后，推荐缓存与 AI 上下文立即失效（TC32）。

### FR04 推荐（Discover）

三个 Tab：

| Tab | 召回 | 说明 |
|---|---|---|
| For you | 全量可推荐用户（排除自己/已拉黑/已跳过冷却/已匹配） | 综合分排序 |
| Language | 与“我”的语言有互补关系 | 语言交换场景 |
| Online | 7 天内有活跃 | 提升“有人回”的概率 |

排序（`backend/app/services/recommend.py`）：

```
score = 0.30·兴趣Jaccard + 0.20·语言互补 + 0.20·时区重叠
      + 0.15·社交目标重合 + 0.15·活跃度(7天线性衰减)
      - 风险扣分（近30天举报，高风险-0.10/中风险-0.05，上限0.30）
      + 新鲜度/偶遇抖动（±小幅度，保证曝光公平与多样性）
```

**硬性合规约束（代码硬编码，不可配置）**：

1. 性别、性取向、宗教、种族等敏感属性**不参与排序**，也不下发。
2. **积分不参与排序**（积分无任何推荐权益）。
3. 房间停留时长不参与排序。
4. 付费/人气加权默认关闭（`RESPONSIBLE_MODE = True`）。

每张卡片下发 `match_hint`：机器生成的一句可解释理由（共同兴趣 / 语言 / 时区），来源仅为公开字段。

验收：TC05 / TC06 / TC07 / TC32；`test_recommend_weights_sum_and_points_not_used`、`test_discover_never_returns_points_or_sensitive`。

### FR05 喜欢 / 跳过 / 匹配

- `POST /likes`：`like` 或 `priority_like`。**重点喜欢**每日 3 次（UTC 日重置），不能花积分购买，作用仅是“优先出现在对方常规喜欢的靠前位置”。
- 对方已喜欢我 → 立即生成匹配（同一对用户**只有一条** match，并发下也只生成一条，用 `UNIQUE(user_a,user_b)` + 冲突处理保证）。
- `POST /passes`：跳过，24h 内不再出现同一人。
- 匹配后双方各得 `FIRST_MATCH` 奖励（见 FR09）。

验收：TC08 / TC09；`test_tc08_concurrent_likes_only_one_match`。

### FR06 聊天

- `GET /matches/{id}/messages?after=ts`、`POST /matches/{id}/messages`。
- 文本 1–2000 字符；客户端携带 `client_msg_id`（幂等：重复提交返回同一条，TC10）。
- **对象级权限**：只有匹配双方可读写；条件不满足返回 404（不泄露资源是否存在，TC40）。
- 任一方向拉黑 → 匹配置为 `closed`，双方都不能再发。
- 消息内容不写日志、不进 AI 上下文（除非用户主动把这些文字交给 AI 工具做翻译/改写）。

### FR07 AI 辅助（核心）

| 任务 | 触发 | 限额（人/日，UTC） | 说明 |
|---|---|---|---|
| ICEBREAKER_V2 破冰 | 匹配聊天页 / 匹配成功页 | 10 | 3 条建议 + 每条来源原因 |
| TRANSFORM_V2 翻译 | 聊天输入框 | 200 | 保留否定、数字、时间 |
| TRANSFORM_V2 改写 | 聊天输入框 | 200 | 不新增事实、不改变承诺/拒绝 |
| ROOM_PROMPT_V1 房间话题 | 主持人房间页 | 5 | 仅用公开房间主题 |
| CALL_PREP_V1 通话准备 | 通话前 | 5 | 仅双方授权信息 |

**不可违反的产品规则**（全部有测试）：

1. AI 只**回填输入框**，发送必须由用户点击（TC11；E2E 断言回填后气泡数仍为 0）。
2. AI 不冒充真人、不生成“已替你发送”。
3. AI 建议基于**已授权的公开字段** + 已审核 RAG；不得国籍→性格。
4. 用户可在设置中关闭 AI（关闭后聊天页/房间页不出现 AI 入口）。
5. 采纳（adopt）记录用于追踪采纳率，但**采纳不发积分**。
6. 失败时降级：`fallback`（模板建议）/ `safety_blocked` / `failed`，UI 明确显示，不阻塞用户。

验收：TC11–TC14、TC34、TC35；E2E `test_discover_like_match_and_ai_fill_only`。

### FR08 语音房

- 房间状态机：`live → ended`；成员角色：`host / speaker / listener`。
- 加入默认 `listener`（TC16）；听众不能发言（TC17）。
- 举手 → 主持人 `approve` / `deny`（TC18）。被移除的成员回到房间列表（TC20）。
- 禁言 speaker：不能发文字/上麦，但仍可听（TC19）。
- 房间消息 ≤500 字；结束房间通知所有成员（TC21）。
- 房间举报生成独立 `report_id`，风险分流（TC22）。
- 房间话题生成只读公开主题，不分析成员、不读私聊（`test_room_rag_topic_uses_public_topic_only`）。
- **不录音**：任何回放/转写能力都不存在。

### FR09 语音通话 + RTC 接通率

- `POST /calls` → `ringing`；对端 `accept` → `accepting`；双方 RTC 上报 `media_ready` → **`connected_at` 才写入**（只写一次）。
- 关键原因：行业内“接通率”口径混乱，如果以“对方点了接听”算接通，会虚高。CrossMate 的定义是 **双方媒体就绪（media_ready）才计接通**，指标才真实。
- `connected_at` 之后才开始计时（E2E 断言）。
- RTC 回调：`POST /rtc/events`，HMAC-SHA256 签名（`ts=<ts>;v1=<sig>` 或对原始 body 的 v1），300s 重放窗口，按 `provider_event_id` 去重（TC24/25）。
  - `AI_MODE=mock`（本地演示）接受未签名事件；**非 mock 一律拒绝未签名**（403/40341）。
- 通话结束可提交质量反馈（1–5 + 标签），每条 ≥3 积分，每周最多 2 次。

验收：TC23–TC27；E2E `test_call_timer_requires_both_media_ready`。

### FR10 通知

- 类型：`match / message / room / reward / safety`。
- `POST /notifications/read` 支持 `{ids}` 或空 body=全部已读；**幂等**（TC37），已读不回退。
- 未读数用于 Tab 角标。

### FR11 积分与激励

| 规则 | 积分 | 次数 | 观察期 |
|---|---|---|---|
| PROFILE_COMPLETE 完成资料 | +20 | 终身 1 次 | 无 |
| FIRST_MATCH 首个匹配 | +10 | 终身 1 次 | 24h |
| FIRST_VALID_INTERACTION 有效互动 | +30 | 终身 1 次 | 24h |
| QUALITY_FEEDBACK 质量反馈 | +3 | 每周 2 次 | 无 |

- **有效互动**定义：24h 内双方各至少 2 条成功送达消息，且无拉黑/违规。
- 观察期内发 spam、被拉黑、违规 → `reversed`（TC29）。
- 周上限 100（UTC 周一 00:00 重置）。
- 兑换：`theme_sunset` 20、`frame_wave` 40；余额不足 409（TC30）。
- **举报永不发积分**（TC31）；积分**不得**为负、不得手工以任何理由凭空发给举报人。

### FR12 举报与安全

- 类别：`harassment / fraud / hate / minor_risk / privacy_request / other`。
- 提交时可选 `also_block`（默认 true）；存储的“证据”只有类别、长度、目标类型等**脱敏信息**，不含聊天原文。
- `SAFETY_TRIAGE_V2` 只做**分流**（`risk_level` + `queue`），**不得直接封号**；人工复核。
- 举报人身份对任何人不可见。
- 举报详情查询需本人或管理员。

## 5. 关键流程

### 5.1 主流程（Happy Path）

```
P01 启动 → P02 登录（18+/条款）→ P03 资料 → P04 兴趣(≥3) → P05 主页
   → P06 Discover（match_hint）→ 双向喜欢 → P07 匹配成功
   → P08 聊天（可选 P09 AI 破冰 → 回填 → 用户点击发送）
   → 双方各 2 条 → 24h 后 FIRST_VALID_INTERACTION +30
   → P12 通话 / P11 房间 → 反馈 +3 → P14 积分兑换
```

### 5.2 异常流（必须在 PRD 里写清，否则实现必然遗漏）

| 场景 | 期望 |
|---|---|
| 验证码 60s 内重发 | 429 码 42901 + `retry_after`，按钮倒计时 |
| 验证码错 5 次 | 429 码 42904（锁定 15 分钟 + `retry_after`） |
| AI 超时/模型错误 | `status=fallback`，给模板建议，提示“AI 暂时不可用” |
| AI 文本含注入 | 不执行，回退安全模板，`fallback_reason=prompt_injection` |
| AI 每日额度用尽 | 429 码 42902（`limit/used`），UI 显示“明天再来” |
| 非成员读聊天 | 404（不泄露存在性） |
| 拉黑后发消息 | 403 码 40322（匹配已 `closed`）；喜欢已拉黑的人 403 码 40321 |
| 余额不足兑换 | 409 码 40920，前端提示差额 |
| RTC 事件签名错误 | 403 码 40341 |
| 双方媒体未就绪 | 不写 `connected_at`、不计时 |

## 6. 我在原需求上做的修正（有据可查）

> 原 v0.2 草稿（仓库根 `README` 提及）存在若干“看起来合理、实现后会出事故”的点，逐条修正如下。

| # | 原设计 | 问题 | 修正 | 影响 |
|---|---|---|---|---|
| C1 | “用户接听即算接通，进入通话时长统计” | 接通率虚高；对端可能永远不加载媒体 | 改为**双方 `media_ready` 后**才写 `connected_at`、才开始计时 | 指标口径变化，需在数据看板同步重算 |
| C2 | AI 建议“一键发送” | 违反“AI 不代替用户”原则；辱骂/诈骗话术可被 AI 放大 | 只回填输入框，发送必须用户点击；有 E2E 断言 | 采纳→发送多一步，但信任与合规不可让 |
| C3 | 兴趣可以小于 3 个就完成资料 | 推荐无特征，冷启动质量差 | 客户端 + 服务端双重校验 ≥3 | 注册转化略降，推荐质量提升 |
| C4 | 时区、国家默认全部公开 | 时区 + 活跃时段可被用来推断作息/位置 | 默认 `matches_only`；不支持从 IP 推断位置 | 隐私边界更清晰 |
| C5 | 举报后给举报人 +5 积分“鼓励监督” | **激励会导致恶意举报** | 举报**不发任何积分**；改为缩短人工响应 SLA | 需监控举报量变化 |
| C6 | 重点喜欢可用积分购买 | 变成“花钱买曝光”，与“积分不影响推荐”自相矛盾 | 积分**不可购买**重点喜欢；每日固定 3 次 | 商业化走订阅/装饰，不走曝光 |
| C7 | 房间成员列表下发完整资料 | 泄露听众隐私 | 只下发 `user_id / nickname / role` | 隐私最小化 |
| C8 | AI 房间话题“分析成员聊天提升气氛” | 违反“不读私聊/不做成员分析” | 只基于公开房间主题生成中性话题 | 功能略降，安全达标 |
| C9 | 通话/房间支持“回放与转写” | 录音是最高风险的数据类型之一 | v0.2 **完全不做**录音/回放/转写 | 少了运营素材，减少合规事故 |
| C10 | 推荐把“房间停留时长”当作权重 | 停留可被脚本刷，且与商业目标耦合 | 权重改为活跃度（7 天衰减）且总权重固定 1.0 | 需埋点 `room_join/room_leave` 用于分析而非排序 |
| C11 | 消息发送只用客户端生成 ID 去重 | 弱网重试仍会重复，或伪造他人 ID | 服务端按 `(match_id, sender, client_msg_id)` 唯一 + 幂等返回 | 弱网体验更好（TC10） |
| C12 | RTC 回调校验“有签名即可” | 攻击者可截获重放 | 校验签名 + 300s 重放窗口 + `provider_event_id` 去重；非 mock 拒绝无签名 | 安全必需 |
| C13 | 资料删除后立即物理删除 | 与举报/风控证据保留、对账冲突 | 软删除（`status=deleted`）+ 脱敏 + token 吊销 + 保留最小合规日志 | 需隐私政策写明保留期限 |
| C14 | 积分规则散落在各页面 | 改一处漏一处，与实现不一致 | 全部常量集中 `backend/app/core/config.py`，PRD/测试引用同一来源 | 可维护性 |
