# CrossMate 指标与数据看板 v0.2

> 读者：产品经理 / 数据分析 / 研发 / 设计。  
> 原则：**每个指标先写定义、口径、数据来源，再谈目标值**。没有口径的数字只是噪音。

---

## 1. 指标设计的三条纪律

1. **口径唯一**：同名指标全公司只有一个定义。例：接通率见 §2.4。
2. **可下钻**：北极星必须能拆到可以直接干预的下一层（见指标树）。
3. **可控与不可控分离**：留存、ARPU 是会受外部市场影响的结果指标；**曝光、喜欢率、AI 采纳率**是团队能直接推动的过程指标。

## 2. 指标字典

### 2.1 规模与活跃

| 指标 | 定义（口径） | 数据来源 |
|---|---|---|
| DAU | 自然日内触达至少 1 个 `app_opened` 的去重用户（UTC 日） | `events.app_opened` |
| WAU / MAU | 7 / 30 天内 `app_opened` 去重 | 同上 |
| DAU/MAU（粘性） | DAU ÷ MAU，反映使用频次 | 衍生 |
| 新用户激活率 | 注册后 7 天内完成资料（`profile_completed=1`）的比例 | `account_created` + `profile_updated` |
| 新用户首匹配率 | 注册后 7 天内产生 `match_created` 的比例 | `match_created` |

### 2.2 匹配与对话漏斗（核心）

```
发现曝光 discover_exposed
  → 喜欢 like_created (+ priority_like_created)
    → 匹配 match_created
      → 打开聊天 chat_opened*
        → AI 建议 icebreaker_generated → 采纳 icebreaker_adopted
          → 首条消息 message_delivered（source=user）
            → 双方各 ≥2 条 → 有效互动（valid_interaction_settled）
```

| 指标 | 定义 | 目标（参考） |
|---|---|---|
| 曝光→喜欢率（Like rate） | 喜欢数 ÷ 曝光数（按人去重会造成偏差，这里按“次”计算与人计算两套） | 8%–15% |
| 匹配率 | 双向喜欢数 ÷ 喜欢数 | 10%–25%（取决于男女比例与算法） |
| 匹配→首条消息（24h） | 24h 内至少 1 条消息的匹配 ÷ 新匹配 | ≥40% |
| **有效对话率** | 双方各 ≥2 条的匹配 ÷ 新匹配 | ≥15% |
| AI 采纳率 | `icebreaker_adopted` ÷ `icebreaker_generated` | ≥25% |
| 采纳→发送率 | 采纳后在 10 分钟内用户点击发送数 ÷ 采纳数 | ≥70% |
| **AI 自动发送次数** | 恒为 0（产品红线，写入看板常驻告警） | =0 |

> `chat_opened` 为前端埋点（进入 `#/chat/:id`）。

### 2.3 付费漏斗（v0.2 为“激励漏斗”，现金付费 v0.3 规划）

当前版本**不现金收费**，用“积分兑换”验证兑换意愿，同时为未来订阅/装饰付费做数据准备：

```
用户 → 获得积分（reward_granted）→ 访问积分页（points_view）→ 兑换（redemption_created）
```

| 指标 | 定义 | 说明 |
|---|---|---|
| 积分活跃率 | 有 ≥1 次 `reward_granted` 的用户 ÷ WAU | 衡量激励体系被感知 |
| 兑换转化率 | `redemption_created` 用户 ÷ 有积分用户 | 虚拟商品需求验证 |
| 人均积分 | 每周发放积分 ÷ WAU | 与周上限 100 对照，判断激励是否过强 |
| 未来付费率 | 若 v0.3 上订阅：订阅成功用户 ÷ WAU | 届时口径固定 |
| ARPPU | 付费用户平均收入 | 仅现金订阅时统计 |
| ROI | （新增付费收入 - 激励/服务器/AI 成本）÷ 成本 | AI 成本按 `ai_generations` 的 token 估算 |

### 2.4 语音（RTC）指标

| 指标 | 定义 | 警惕 |
|---|---|---|
| 呼叫发起数 | `call_requested` | — |
| 接听率 | 对端 accept ÷ 发起 | 只看用户动作 |
| **接通率（CrossMate 口径）** | `call_connected`（双方 media_ready 且首次）÷ `call_requested` | 若用“接听”当接通，会虚高 10–20 个百分点 |
| 接通时长 | `call_ended.duration` 的中位数 | 均值会被长通话拉高 |
| 接通失败原因分布 | `rtc_events` 中 `error_code` | 网络 vs 设备权限 vs 对端退出 |
| 房间到场→上麦率 | `speaker_approved` ÷ `room_joined` | 过低说明主持人审核慢或门槛高 |

### 2.5 留存与同期群

- 留存口径：D1/D7/D30 = 首次 `app_opened` 后第 N 天仍 `app_opened` 的用户 ÷ 同期新用户。
- **同期群（cohort）** 按注册周分组，观察：D7 留存 × 首周是否产生过有效互动。预期结论：**首周有效互动者的 D30 留存显著高于没有的人** —— 这是把资源投入“匹配→对话”而不是“多刷卡片”的证据。

| 同期群 | D1 | D7 | D30 | 备注 |
|---|---|---|---|---|
| 2026-W45（冷启动） | 38% | 16% | — | 种子用户 |
| 2026-W46（AI 破冰上线） | 41% | 19% | — | 关注采纳→发送率 |
| （示例数据，上线后替换为真实值） | | | | |

### 2.6 体验与效率

| 指标 | 定义 |
|---|---|
| AI 生成成功率 | `status=succeeded` ÷ 总生成 |
| AI fallback / safety_blocked 占比 | 按 `fallback_reason` 分桶，`prompt_injection` 单独监控（异常升高=被攻击） |
| P95 接口延迟 | 按路由统计（房间列表、Discover、消息列表） |
| 崩溃/5xx 率 | E2E 中已断言无 5xx |
| 举报量 / 千人举报率 | `report_submitted` ÷ 1000 WAU；按类别、按 `risk_level` |
| 举报 24h 首次响应率 | 人工工单系统（本仓库只做分流，执行层在外部） |

## 3. 曝光→转化全景漏斗（示例周）

| 步骤 | 数值 | 步间转化 | 累计 |
|---|---|---|---|
| 发现曝光 | 120,000 | — | — |
| 喜欢 | 12,600 | 10.5% | 10.5% |
| 匹配 | 2,520 | 20.0% | 2.1% |
| 首条消息（24h） | 1,310 | 52% | 1.1% |
| 双方各 ≥2 条 | 630 | 48% | 0.53% |
| 语音通话接通 | 190 | 30%（有效对话→通话） | 0.16% |

解读方法：哪一步的转化与本象限的行业基准差距最大，就集中做那一环的实验。例如“首条消息率最低”→ 优先改 AI 破冰与匹配成功页。

## 4. A/B 实验规范

- 分流单位：用户 ID 哈希；同一实验内比例稳定。
- 样本量：二分类指标按 α=0.05、power=0.8 估算；**事前注册**指标与停止规则。
- 观察期：至少覆盖一个完整周（排除周末效应）。
- 护栏指标：崩溃率、举报率、AI 自动发送次数、消息发送失败率。

**本季度实验清单**

| # | 假设 | 指标 | 护栏 |
|---|---|---|---|
| E1 | 匹配成功页展示“为什么推荐你们聊天”能提升首条消息率 | 匹配→24h 首条消息率 | 举报率不升 |
| E2 | AI 破冰建议给“来源原因”能提升采纳率 | icebreaker_adopted ÷ generated | 采纳→发送率不降 |
| E3 | Discover 首屏从 10 人改 6 人 + 提前加载 | 曝光→喜欢率、P95 延迟 | 喜欢率 |
| E4 | 语音房“举手”改为“排队序号”降低听众焦虑 | 到场→上麦率 | 房间停留 |
| E5 | 每日重点喜欢 3→2 次 | 喜欢率、匹配率 | 留存 |

## 5. 男女比例平衡（双边供给）

平台早期常见失衡（男 >> 女）会直接压低女性的曝光与体验，进而流失。**CrossMate 不在排序中用性别**（合规底线），改用“供需健康度”指标管理：

| 指标 | 定义 | 目标带 |
|---|---|---|
| 性别比 | 日活跃男性 ÷ 日活跃女性（只用于内部供给分析，**不进入排序**） | 2:1 以内 |
| 女性收到喜欢的质量 | 女性收到喜欢中“对方资料完整度≥60%”的比例 | ≥60% |
| 女性首日举报率 | 女性新用户 24h 内 `report_submitted` 占比 | <3% |
| 男性曝光满足度 | 男性浏览后“有可喜欢对象”的比例 | ≥80% |

干预手段（**不作用于排序公式**）：地域/语言冷启动招募、新人保护（低风险优先展示给资深用户）、女性侧的一键“只接受已验证用户”偏好。

## 6. 本地化

| 市场 | 语言优先级 | 关键本地化点 |
|---|---|---|
| 印尼 / 菲律宾 | English, Bahasa, Filipino | 夜间活跃（21:00–01:00 本地时间），轻量流量包 |
| 巴西 | PT-BR | 语音房 > 文字；足球/桑巴兴趣标签 |
| 海湾（UAE/沙特） | English, العربية | 更保守的可见性默认值、性别交互偏好前置声明 |
| 日本 | 日本語, English | 礼貌语风格（`style=polite`）、少直接问问题 |

时区不是简单的横幅文案：推荐中的**时区重叠**权重（0.20）就是为了让“在线时间对得上”的人相遇；房间按“本地时间晚间”排序。

> **界面语言 ≠ 目标市场**。v0.2 的界面支持 en / zh / ja / es（`web/js/i18n.js`），但目标市场表里没有中国大陆：
> 中文主要服务海外华人和语言交换用户（演示账号 `alex` 的语言就是 English + 中文）。
> 界面语言只翻译骨架文案；用户内容和 AI 输出不翻译——翻译用户的话等于替他们表达。

## 7. 看板（可直接落地的 SQL / 端点）

- 现成端点：`GET /api/v0.2/admin/stats` → 当日 DAU 与各事件累计计数。
- 用 `events` 表即可算出的核心视图：

```sql
-- 每日漏斗（按 UTC 日）
WITH d AS (SELECT user_id, name, date(created_at,'unixepoch') AS day FROM events)
SELECT day,
  COUNT(DISTINCT CASE WHEN name='discover_exposed' THEN user_id END) AS exposed_users,
  COUNT(DISTINCT CASE WHEN name='like_created' THEN user_id END) AS likers,
  COUNT(DISTINCT CASE WHEN name='match_created' THEN user_id END) AS matched
FROM d GROUP BY day;

-- 有效对话率（按周）：双方消息≥2 的匹配 ÷ 新匹配
SELECT week, ROUND(1.0*valid/total,3) AS valid_rate FROM (
  SELECT strftime('%Y-W%W', created_at,'unixepoch') AS week, COUNT(*) AS total,
         SUM(CASE WHEN valid=1 THEN 1 ELSE 0 END) AS valid
  FROM matches GROUP BY week);
```
