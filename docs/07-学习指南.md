# CrossMate 学习指南：从 0 复刻一遍，拿下社交 / AI PM 面试

> 写给：有一定产品感觉、但没做过完整社交产品的你。  
> 目标：**8 天独立复刻**，能在面试里把「为什么这么做 → 怎么做 → 数据怎么验证」讲成一个闭环。  
> 配套：`docs/00`–`06`，代码在 `backend/`、`web/`；每读完一节都去看对应代码，边读边改是最高效的学习方式。

---

## 0. 先建立三个判断

1. **社交产品的本质不是“匹配到一个”，而是“聊起来”。** 匹配只是漏斗中间层。你要能回答：匹配之后，两个人为什么会有第一条消息？
2. **AI 在社交产品里最大的风险是“越界”。** 冒充真人、代替说话、推荐理由造假——每一个都能换来短期数据，代价是长期信任。
3. **每个指标都有一个“听起来更漂亮但不可信”的版本。** 例如接通率用“点击接听”算会虚高；留存用“打开 app”算会虚高。**你定义口径的能力，就是产品经理的专业度。**

## 2. 项目精读顺序（按“一个用户的第一次使用”）

### 2.1 启动 → 登录（P01–P02）

代码：`web/js/app.js` 的 `renderSplash / renderLogin`，`backend/app/routers/auth.py`。

读的时候问自己：

- 为什么“18+ 与条款”在**客户端**先拦一次，服务端**还要**再校验？（答：前端是体验，后端是合规底线，前端可被绕过）
- 验证码锁定为什么用 429 而不是 401/400？（答：语义是“别太快”，客户端需要对 `retry_after` 做倒计时）
- 演示模式为什么直接返回验证码？（答：可演示、可测试；生产必须走邮件，代码用 `demo_code` 字段隔离）

**动手**：把 `CODE_RESEND_SECONDS` 从 60 改成 10，跑 `test_tc03_resend_within_60s_returns_429`，看它为什么失败（然后改回）。

### 2.2 资料（P03–P04）

代码：`users.py::patch_profile`、`public_view`。

关键点：

- `profile_strength` 是加权完成度，影响推荐轻微加权，但**不决定曝光**（避免“资料党”霸屏）。
- 兴趣 ≥3 是双重校验。为什么不是“越填越好”？（答：越多越难一致，反而稀释共同点；同时对用户是负担）
- **邮箱永不出现在 `public_view`**：把这条写进你自己的隐私检查清单。

### 2.3 发现（P06）——最重要的 40 行代码

代码：`services/recommend.py`。

```
score = 0.30·兴趣 + 0.20·语言互补 + 0.20·时区 + 0.15·目标 + 0.15·活跃 - 风险 + 抖动
```

逐个回答：

1. 为什么时区占 0.20？——跨时区社交的“在线时间对不上”是最常见的失败原因。
2. 为什么风险是**扣分项**而不是“权重”？——风险不是偏好问题，是底线问题。
3. 为什么有“抖动”？——曝光公平与多样性；也防止同一批人长期霸占首屏。
4. 哪些东西**故意不在公式里**？敏感属性、积分、房间停留时长、付费。这是面试必答题。
5. `match_hint` 怎么来？——规则模板，不用 LLM（确定性、零成本、可测试）。

**动手**：把 `interest` 权重改成 0.6，观察右上角“合计 1.0”的测试（`test_recommend_weights_sum_and_points_not_used`）如何提醒你。

### 2.4 喜欢 → 匹配（P07）

代码：`discover.py::create_like / _create_match_if_reciprocal`。

面试常问“并发怎么办”。答案：`UNIQUE(user_a,user_b)` + `INSERT OR IGNORE`，先排序两人 id 保证唯一键稳定；`test_tc08_concurrent_likes_only_one_match` 用并发请求验证。

### 2.5 聊天 + AI（P08–P09）

代码：`discover.py::send_message`、`ai.py`、`services/ai_engine.py`。

- 幂等：`client_message_id` 唯一，重试返回同一条（TC10）。
- AI 采纳：`POST /ai/adopt` 返回 `"sent": false`；前端只写输入框。**这是整个项目最值得讲的设计**：把“AI 的效率”和“用户的自主”分开。
- Prompt：先读 `GLOBAL.md`，再读 `ICEBREAKER_V2.md`。注意每个反例（国籍推断、已替发送）。
- 护栏：输入层注入检测 → 输出层角色检测 → Schema 校验 → 一次修复 → fallback。

**动手实验**（加深印象）：

```bash
# 让模型永远“超时”，观察降级
# tests 里已用 monkeypatch 做过；你也可以在 ai_engine.call_model 里临时 return None, "model_error:TimeoutError"
```
观察：用户仍能正常聊天，只是 AI 建议变成模板；且额度被退还（`refund_quota`）。

### 2.6 房间与通话（P10–P12）

代码：`rooms.py`。

- 状态机：`listener →（举手）→ pending →（主持人批准）→ speaker`；`deny` 会通知。
- 权限：非成员读房间消息 404/403；下发的成员信息只有 id/昵称/角色。
- 通话最关键的三个点：① 双方 `media_ready` 才 `connected_at`；② 签名 + 300s 重放窗口 + 事件去重；③ 计时从 `connected_at` 开始。
- 为什么 mock 模式允许未签名事件？（答：本地演示没有真实 RTC 服务；但**非 mock 必须拒绝**，有测试 `test_rtc_unsigned_rejected_when_not_mock`）

### 2.7 积分与举报（P14 / P17）

- 积分账本：pending → granted / reversed；周上限 100；兑换 409 余额不足。
- 举报：**只存脱敏证据**、**不发积分**、**只分流不封禁**。这三条都是针对“看起来合理其实有害”的设计做的修正。

### 2.8 隐私（P16）

- 字段级可见性，服务端过滤。
- 导出：不含 token、不含他人消息。
- 注销：软删除 + token 吊销 + 不再被推荐（TC33）。

### 2.9 会话列表与设置（P19 / P18）

代码：`web/js/app.js` 的 `renderChats`、`renderSettings`，以及 `web/js/i18n.js`。

- **Matches 和 All 必须是两件事**：Matches = 已匹配但**还没聊过**（这是"还没开始的对话"，是最需要推动的一批人）；
  All = 全部会话。两者底部都要有数量角标。这一条看着像细节，其实是留存问题的入口——
  用户打开 App 最该看到的是"有人等你开口"，而不是被读过的会话淹没。
- **设置里每一行都必须是真能用的**：昵称（走 `PATCH /users/me/profile`）、语言（`#langRow`）、
  通知开关（存 `localStorage.cm_notify`）。凡是带 `›` 的，点下去必须有结果。
- **i18n 的边界**：`web/js/i18n.js` 只翻译**界面骨架**（导航、设置、启动页、空状态）。
  用户产出的内容（昵称、聊天、房间名、AI 建议）**不翻译**——翻译别人的话就是在替他们说话，
  和"AI 不冒充用户"是同一条原则。语言存 `localStorage.cm_lang`，并同步 `<html lang>`（读屏依赖它）。
- 面试可以讲的一句话：**"我们只做界面本地化，不做内容本地化，因为后者会改变用户表达的意思。"**

### 2.10 怎么保证“每个按钮都能点”（这一节最值得面试讲）

背景：上线前用户反馈"连最简单的语言都切换不了"。排查发现设置页的「语言」一行带 `›` 箭头、
看起来完全能点，其实是 `<span>`，**一个事件都没绑**。而当时 57 个接口测试、6 个主流程 E2E 全绿。

**教训：主流程测试只证明"happy path 能走通"，证明不了"每个控件都有反应"。**

做法（`e2e/test_clickable.py`）：把 11 个页面里所有"看起来能点"的元素全找出来，逐个真实点击，
1.1 秒内出现下列**任一**变化才判通过——路由跳转 / 重渲染 / 弹层 / toast / 本地存储变化 /
下拉值变化 / `aria-pressed`、`aria-checked`、class 变化 / 元素被移除 / 发出新的 API 请求 / 弹出确认框。

三个设计细节值得讲：

1. **为什么要有"排除项"**：当前所在 Tab 点了只回顶部（设计如此）；余额不足已 `disabled` 的兑换按钮不点
   （禁用是对的）；点击超时（被弹层遮住）不算失败。**判据把"设计上不该有反应"排除掉，否则测试会逼你做错事。**
2. **为什么语言切换单独写一条回归**：用户报过的问题必须有一条测试永远盯着它。断言是端到端的——
   点语言 → 中文 → 底部 Tab 变成"首页/发现/房间/聊天/我的" → `<html lang>` 变了 → **刷新后还记得**。
3. **为什么真机验证要用真实触摸事件**：`evaluate('btn.click()')` 会绕过命中区域、遮挡和手势层。
   同一批问题里，"底部 Tab 可点区域只有 17px 宽"只有用真实触摸（CDP `Input.dispatchTouchEvent`）才测得出来。

同一轮还顺出来 9 个同类问题：Chats 两个子标签内容一样、积分兑换永不禁用、社交登录假装是真实授权、
条款链接点不开、通话静音按钮是死的、设置页昵称/通知两行是死的……这些都是**"有 UI 没行为"**。

> 面试话术：**"我们不是靠背测试数量来保证质量的。我们是先问'用户会点哪里，点了应该发生什么'，
> 再让机器替我们点一遍。测试跑绿不代表没问题，测的东西对不对才是关键。"**

## 3. 你要能独立复现的关键代码

| 模块 | 行数级别 | 复现标准 |
|---|---|---|
| 统一响应 + 错误码 | ~80 | 所有错误 `{code,message,data,request_id}` |
| 验证码 + 会话 | ~120 | 5 分钟过期、60s 重发、5 次锁定 |
| 资料 + 隐私过滤 | ~100 | `public_view` 永不泄露邮箱/隐私字段 |
| 推荐排序 | ~80 | 权重合计 1.0 + 风险扣分 + 抖动 |
| 双向匹配 | ~40 | 并发只生成一条 |
| 消息幂等 | ~30 | 同一 `client_message_id` 重复返回同一条 |
| AI 编排 | ~250 | 权限→配额→上下文→注入→模型→校验→降级→落库 |
| RTC 校验 | ~60 | HMAC + ts + 去重 |
| 积分账本 | ~150 | pending→granted/reversed + 周上限 |
| 前端路由 | ~60 | hash 路由 + query + 401 登出 |

复现顺序建议：**后端接口 → 测试 → 前端页面**。先有测试，前端联调时你会省一半时间。

## 5. 面试问答脚本（10 题，每题 2 分钟以内）

### Q1 介绍一下这个项目

> CrossMate 是一个面向海外青年的轻社交产品原型，我做完了 18 个页面、一套 API 和完整的测试。核心判断是：**社交产品的价值在“聊起来”，不在“匹配到”**，所以我定的北极星是周均有意义对话用户数。最关键的差异化是两条：推荐要可解释（告诉用户为什么推荐你们聊），AI 只给建议、绝不代替用户说话。

### Q2 你们的匹配算法怎么做的？

> 五个特征加权：兴趣重合 0.3、语言互补 0.2、时区重叠 0.2、社交目标 0.15、活跃度 0.15，再减去近 30 天的风险扣分，最后加一点曝光公平的抖动。**故意不用的**：性别等敏感属性、积分、房间停留时长、付费加权。理由分别是合规、防止“花钱买曝光”和防止被脚本刷。卡片上还有 match_hint，用规则生成而不走 LLM，保证可解释、零成本、可回归测试。

### Q3 为什么接通率要用“双方 media ready”定义？

> 如果以“对端点了接听”算接通，会高估 10–20 个点，因为媒体可能有权限或网络问题永远连不上。我们用 RTC 回调里双方的 media_ready 作为唯一触发点，并且只写一次 `connected_at`；事件用签名 + 300 秒重放窗口 + provider_event_id 去重。这样这个指标可以直接用于对 RTC 供应商的 SLA 谈判。

### Q4 AI 怎么保证不越界？

> 四层：输入层检测注入；权限层只允许匹配成员、只使用已授权字段；Prompt 层写死“你不是真人、只给建议、不得国籍推断”；输出层做角色越位检测和 Schema 校验，失败降级成模板。产品层还有一条：建议只回填输入框，发送必须用户点击——这有 E2E 断言，不是口头承诺。

### Q5 你做过哪些“修正别人需求”的判断？

> 比如原需求里举报给积分，我改掉了，因为激励会催生恶意举报；重点喜欢原设计能用积分买，我改成每日固定 3 次，否则和“积分不影响推荐”自相矛盾；通话原来“接听即算接通”我也改了。PRD 里有一张 14 条的修正表，每条都写了原因和影响。

### Q6 怎么衡量 AI 功能有没有用？

> 三个数：生成成功率（排除模型问题）、采纳率（建议有没有被用）、采纳→发送率（用了之后有没有真的发出去）。还有一个常驻告警：AI 自动发送次数必须恒为 0。如果采纳率涨了但发送率跌了，说明建议质量有问题。

### Q7 男女比例失衡怎么处理？

> 首先排序里不用性别，这是底线。然后用供需指标管理：女性收到喜欢的质量、女性首日举报率、男性曝光满足度。手段是地域和语言的冷启动、新人保护、以及给女性的一键“只看已验证用户”偏好。这些都不碰排序公式。

### Q8 为什么不做现金礼物？

> 因为现金礼物会诱导“付费换曝光/换关注”，和“积分不影响推荐”直接冲突，而且在很多出海市场有合规风险。v0.2 用非现金的积分兑换装饰来验证兑换意愿，数据够了再考虑订阅。

### Q9 你怎么验证一个想法？

> 先写假设和指标，再定样本与停止规则，护栏指标一定要有。比如“匹配页加推荐理由能提升首条消息率”，主指标是 24h 首条消息率，护栏是举报率不升。观察一个完整周排除周末效应。

### Q10 这个项目最大的不足是什么？

> 实时性是轮询，不是 WebSocket；存储是 SQLite 单机；AI 用的是确定性 mock，真实模型的语义保真还没用人工标注集评估过。我的 v0.3 计划是先接真实模型做离线评估，再上 WebSocket 和 PostgreSQL。先说不足，再说怎么补，比假装完美更可信。
